## 2. What is done

### 2.1 Backend — 70 routes, twelve `v1` routers plus health

| Area | Routes | Notes |
|---|---|---|
| Identity | `GET/PATCH /v1/me` | Supabase Auth client-side; the first `GET /v1/me` materialises the user and reports `needs_onboarding` |
| Workspaces and members | 9 | roles `viewer`→`owner`, one owner per workspace by partial unique index, promotion is a transfer in one transaction |
| Projects | 5 | |
| API keys | 4 | hashed, scoped (`ingest`, `full`), revoke and delete |
| Credentials | 5 | envelope encryption, AAD bound to workspace **and** credential id, rotate, revoke |
| Agents | 15 | list, create, read, patch, archive, restore, `test`, status history, runs, executions; model profiles CRUD |
| Project runs | 1 | `GET /v1/projects/{id}/runs`, including the quiet-run view |
| Workflows | 14 | connections and grants, workflows, versions, draft `GET`/`PUT`, `validate`, `publish`, `restore`, archive |
| Executions | 6 | run, list, read, cancel |
| Dispatch review | 2 | the queue at `viewer`, `resolve` at `admin` under `dispatch.resolve_review` |
| Ingest | 4 | events (partial success), heartbeat, logs, metrics |
| Meta and health | 3 | |

**Orchestration.** `advance()` is a pure decision function — no clock, no I/O, asserted
from its own syntax tree — and `services/executions.py` applies its decisions as one
transaction: event, state, outbox row. Dispatch rows are written from exactly one file,
enforced by a containment allow-list split by verb: `repositories/dispatches.py` may
*update* a dispatch but may not *insert* one.

**Workers.** `agentworld-worker` and `agentworld-reaper` are real processes with `--once`
and continuous modes, deliberately outside the API lifespan. Claiming is
`FOR UPDATE SKIP LOCKED` plus a lease. `side_effect_started_at` is written **before** the
outbound call, so an expired lease can tell "never sent" from "might have landed": the
first is retried, the second becomes `needs_review` and waits for a human. The reaper also
runs a reconciliation sweep for executions that are consistent but stalled.

**Outbound security.** One guarded HTTP client: resolve, validate every resolved address,
pin the connection to a validated one, no redirects followed. Both IP families, the
metadata addresses and names, NAT64 and the short/hex/octal loopback forms are all refused,
and a blocked destination renders the same string as a refused socket. `httpx` is confined
to `infra/net/` by an import contract with one named Supabase exemption.

**Providers.** The Anthropic Messages API is spoken directly — no vendor SDK, so "every
provider call goes through the guarded client" cannot be broken by an internal of theirs.
A source search covers what no import contract can see: a vendor's name in a string, a
constant or a comment.

**Event sourcing.** Append-only `events` with per-project `seq`, dedup keys, partitioning,
reducers with out-of-order tolerance, and the two properties that keep it honest: refolding
the stored log reproduces the state, and folding it creates **zero** dispatch rows.

**Tests and enforcement.** 48 integration and 27 unit test files; 8 import-linter
contracts; schema/enum drift tests against a freshly migrated database; an exhaustive role
matrix with a non-vacuity guard; migrations applied from scratch in CI. Three CI jobs —
`api`, `web`, `compose` — and the compose job asserts the application role cannot bypass
RLS.

### 2.2 Web app — 7 pages

| Page | What it does |
|---|---|
| `/` | the one page that handles every session state: setup instructions, sign-in, workspace, or an honest "the API is down" |
| `/login` | Supabase sign-in, deep-link preservation, and the rejected-token recovery path |
| `/auth/callback`, `/auth/signout` | code exchange; sign-out at the library's global scope, answering 303 |
| `/onboarding` | create the first workspace and project |
| `/w/{ws}` | project list |
| `/w/{ws}/keys` | mint and revoke API keys |
| `/w/{ws}/p/{p}/agents` | the project's agents |
| `/w/{ws}/p/{p}/agents/{id}` | one agent: status, heartbeat, details |

Typed clients for tenancy and agents, a problem-details-aware fetch wrapper, middleware
that forwards the real return path so a deep link survives sign-in, and 160 tests across 9
files with `tsc --noEmit` and `eslint .` clean.

Three auth defects were found and fixed by probing rather than by reading, on 2026-11-16:
deep links were dropped at sign-in, the middleware matcher missed workspace routes
containing a dot, and a Supabase session the API rejected bounced `/` ↔ `/login` for ever.

### 2.3 Infrastructure

Docker compose stack with Postgres, a health-gated startup, an application role that cannot
bypass RLS, Alembic migrations with a from-scratch CI check, and runner tasks for every
loop a developer needs (`npm run dev`, `test`, `lint`, `typecheck`, `verify`, `api:worker`,
`api:reaper`, `infra:up`).

## 3. What is not done

### 3.1 Phase 3, Track A — four items

1. **The event bus and the WebSocket gateway.** `api/ws/__init__.py` is a one-line
   placeholder. No `POST /v1/projects/{id}/ws-ticket`, no snapshot, no deltas, no cursors,
   no `resume`, no `resync_required`. This is the largest outstanding piece of Phase 3 and
   the island's statuses are specified to come from it.
2. **The OpenAI-compatible provider (T13)** — named in the plan as the last task of the
   phase, written specifically to prove the protocol is not shaped around one vendor. The
   shared conformance suite its acceptance criterion names does not exist either; it would
   be extracted from the Anthropic tests.
3. **T7, the managed-agent turn loop.** What exists is one model call per step:
   `services/dispatch.py`'s own comment says *"the conversation loop - tool results fed
   back, several turns per step - is T7's"*. No `max_turns`, no wall clock, and no token
   counts or durations reaching `metric_samples`.
4. **T8's decision layer.** Retries, jittered backoff, dead letters and uncertain outcomes
   exist on the dispatch row, but `RetryStep` is deliberately absent from `advance()`
   (`decisions.py` says it "arrives with the retry policy, in T8"), and
   `workflow_steps.on_failure` is a column no code reads. A worker that needs longer
   cannot extend its own lease either, which is a T6 criterion.

**A live provider call is not on this list, and the earlier draft of this file was wrong
to put it there.** One was made during T6 against a real model, measured over five runs,
and it found three defects - an attempt budget never consumed, a terminal 400 retried, and
an empty answer recorded as success (`15-T6-WORKER.md` §10). What remains unrun is T3's
`scripts/live_provider_smoke.py`, a narrower check needing an `ANTHROPIC_API_KEY`, and the
formal criterion's wording - a run driven through `POST .../run` with `curl`.

### 3.2 Phase 3, Track B — nothing built

`apps/web/world/` holds a README. Phaser and Zustand are in no `package.json`. The
`world_nodes`, `world_routes`, `world_districts` and `world_layouts` tables exist with no
endpoints in front of them. Of the "minimal pages", the agent list and detail exist; **the
agent form and the execution detail page do not**, so an agent cannot be created or
configured, and an execution cannot be read, without `curl`.

### 3.3 Everything after

Phase 3a (approvals, MCP tool execution, dispatchable agents), the rest of Phase 4, and
Phases 5–11. Nothing in them has started.

## 4. Open gaps and risks

**Reliability**

- **Stalled executions.** Settling or resolving a dispatch commits in one transaction;
  `advance_once` runs in a second, because it decides from committed state. A process that
  dies between them leaves an execution complete, consistent and **stalled**. T6c narrows
  this to "somebody comes back within the sweep interval plus the grace period"; it is not
  closed.
- **`needs_review` is terminal without a human.** A lease that expires mid-flight is never
  retried automatically — by design, because nobody knows whether the effect landed.
  `POST .../dispatches/{id}/resolve` is the only way out, at `admin`, with a mandatory note
  and an explicit acknowledgement that a retry may repeat the effect.

**Capability**

- `tool_call` steps cannot be published: the check constraint needs a `tool_id` and there
  is no `tools` table until Phase 6. `advance()`'s tool_call branch is tested and
  unreachable from a published workflow.
- Consequential external actions are **refused at publish**, not gated, until Phase 3a
  replaces the refusal with an approval.

**Security, stated honestly**

- Prompt injection choosing an *allowed* destination is not solved. The guarded client
  stops an agent reaching an internal address; it does not stop a malicious document
  telling an agent to POST to an attacker's public URL. The mitigations listed in the
  proposal's README are a **gate on Phase 6**, not an audit item — including an adversarial
  test that asserts the exfiltration *succeeds*, so the limitation lives in CI rather than
  in memory.

**Web**

- `readSession` labels a 403 as `api-unreachable`; that is authorization, not an outage.
- A malformed agent id surfaces the API's `"1 field(s) failed validation"` verbatim.
- `expectsHeartbeat` duplicates the API's liveness rule in the client.
- `outcomeOf`'s agent-branch fallback is untested; the bearer token is unasserted in
  `agent-overview-load.test.ts`; `middleware-matcher.test.ts` passes `{}` as `nextConfig`;
  a stale `.pill--warn` comment sits in `lib/agents/presentation.ts`.
- **No `.tsx` file is under test.** Vitest runs in `node` with no jsdom, so page markup is
  covered by live probes and comments only. Anything whose correctness must be *asserted*
  belongs in a pure `.ts` module — which is why the redirect decisions were extracted into
  `lib/auth/destination.ts`.

## 5. The roadmap from here

### Next six steps, in order

| | Step | Size | Done when |
|---|---|---|---|
| **N1** | Runs, status history and executions on the agent detail page | ~1 session | an operator can see what an agent has done, with the empty, quiet and failed cases each rendering something actionable. `listRuns`, `listStatusHistory` and `listExecutions` are already written and called from nowhere |
| **N2** | Agent create/edit form + execution detail page | 1–2 sessions | an agent can be created, re-pointed at another model profile, archived and restored, and an execution's steps read, without `curl`. Closes Track B's "minimal pages" |
| **N3** | The realtime spine: event bus, `ws-ticket`, gateway | ~1 week | two `websocat` sessions on different API processes see identical deltas, and killing one mid-stream loses nothing on reconnect |
| **N4** | OpenAI-compatible provider *(independent — can run in parallel)* | ~2 days | the same workflow runs against both providers with no change outside `infra/providers/`, and the SDK contract still fails on a planted violation |
| **N5** | Reconcile what remains of Phase 3's ledger | ~½ session | the three open Track A boxes are either ticked with a named test or recorded as wrong; Phase 3 can then be *declared* done and mean it |
| **N6** | Island skeleton I1 | ~1 week | the island shows real agents with real statuses, no mock-data path exists, and deleting `world/phaser/` leaves the backend and non-world web suites green. Needs N3 and the missing `world/nodes` endpoints |

**Why this order.** N1 and N2 are cheap, need no new endpoint, and close the gap between
what the backend does and what anyone can see. N3 comes before the island because the
island's statuses are specified to come from live deltas — the other order builds that
feed twice. N4 is independent of all of it.

## 6. The decision worth making before N1

Phase 3's gate is *a real end-to-end managed execution, driven by `curl`, with no
frontend*. N1 and N2 do not move that gate; they make its results visible.

- To **declare Phase 3 complete**: N4 → N5 → N3.
- To get **a product someone can use**: N1 → N2 → N3.

About two weeks apart, and a different risk carried either way: the first leaves the
product unusable for longer, the second leaves a phase open while building on it.
